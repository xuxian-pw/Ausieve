# 音频管线：来之不易的结论

每一条都是先测量出现象、再在 RustDesk 上听过确认的。修改相关代码前，先用测量证明它不成立。

- **输出必须用独占模式。** EXCLUDE 模式会采集所有端点上的共享模式流，其中包括我们自己写进 Line 1 的那一路。用共享模式输出会无限回环（t3）。独占流绕过引擎混音器，所以不会被采到。
- **Process loopback 会丢音频，这是 Windows 本身的问题。** 系统里任何程序打开或关闭一个流时，丢一次大约 40ms：先是 5–11ms 的时间戳跳跃，然后是约 31ms 的精确零，并且不带任何 flag。device loopback 在同样情况下不丢。采集缓冲区大小对此没有影响：设成 5 秒（与 OBS、win-capture-audio 相同）只是防止系统卡顿时溢出，不增加延迟。
- **断点按 OBS 的方式处理**（`src/timeline.rs`）：根据 QPC 时间戳，丢了多长就补多长的静音，两侧各加 3ms 淡出/淡入。补进去的只能是静音。`9a0080f` 试过用前面的音频合成来填补空缺，结果出现明显电音，已在 `f1c2f76` 撤回。
- **漂移控制只用来跟踪两个设备之间缓慢的时钟偏差。** 改速时会对每个采样做三次插值，打在“叮”这种高频丰富的短音上，就是轻微的“滋啦”。所以它的修正必须慢到不会落在单个短音上，水位因断点下降要靠补静音恢复，不靠改速。
- **独占输出不能欠载。** 欠载时 Windows 会重放缓冲区里的旧数据，听起来是咔哒声。抖动缓冲先预填一段再开始播放，数据不够时补静音；它会保留最后 3ms，这样晚到的包也有音频可以做淡出。
- **API 只能排除一棵进程树。** 托盘程序和 `--exclude-path` 都按 exe 的完整路径找根进程。
- RustDesk 连续收到约 800 帧全零后会停止编码（`AudioEncoder::should_encode`）。为此加了“静音底噪”开关（默认关），但 A/B 对比证明这不是杂音的原因。
