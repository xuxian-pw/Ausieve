# audio-exclude

**Capture all Windows system audio except one program, and feed it into a virtual audio cable** —
e.g. so a remote-desktop tool such as RustDesk can stream the host's sound without echoing the
host's voice-chat app (similar to Parsec's "exclude application" option).
Uses WASAPI *process loopback* (`PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`).

把 Windows 上**除某个程序以外**的所有声音实时转进虚拟声卡。典型用途：远控被控端同时开着 Discord 等语音软件时，
RustDesk 采集系统声音会把语音软件的声音也传给对方，造成回音；用本工具排除语音软件，再让 RustDesk 采集虚拟声卡即可。

## 前置条件

- Windows 10 2004（build 19041）或更高版本，Process Loopback API 从这个版本开始提供。
- 一个虚拟声卡，例如 [VB-Audio Virtual Cable](https://vb-audio.com/Cable/) 或 Virtual Audio Cable (VAC)。
  它要有一对播放端/录音端，并允许独占模式（Windows 默认允许）。
- 从源码构建需要 Rust stable，工具链为 `x86_64-pc-windows-msvc`，并安装 Visual Studio Build Tools 的 C++ 组件（提供链接器）。

## 构建

```powershell
cargo build --release
```

生成三个程序：

- `target\release\tray.exe`：托盘程序，日常使用推荐它。
- `target\release\capture.exe`：命令行版本。
- `target\release\tone.exe`：测试辅助程序。

## 托盘程序（推荐）

双击 `tray.exe`，它会常驻系统托盘，没有控制台窗口。左键或右键单击图标打开菜单：

```
排除 Discord.exe（运行中，PID 1234）        ← 当前状态（灰色，不可点）
输出：Line 1 (Virtual Audio Cable) (48000 Hz I16)
──────────
排除哪个程序（一次只能排除一个）
 ○ 不排除（转发全部声音）
 ● Discord.exe
 ○ voice.exe（未运行）
──────────
添加程序…                                   ← 弹出文件选择框，选 .exe
移除程序（显示完整路径） ▸
输出设备 ▸                                   ← 选择写入哪个播放设备
缓冲 / 延迟（20 ms） ▸                        ← 11/12/15/20/30 ms
静音时输出微弱底噪（防远端静音门限）          ← 开关，默认关
打开配置文件夹
──────────
退出
```

- **添加程序**：选中一个 `.exe` 后，它会加入列表并**立即被选中**。列表里显示文件名；两个程序同名时，括号里会注明所在文件夹。完整路径可以在“移除程序”子菜单里看到。
- **快速切换**：点列表里的某一项，马上切到排除它，不用重启。受 API 限制一次只能排除一个程序，所以列表是单选（圆点）。
- **按完整路径匹配**：只排除路径完全相同的那个 exe，同名的其他程序不受影响。程序还没启动、已经退出或重启后，都会自动跟上。程序没在运行时转发全部声音。
- **状态和错误**：鼠标悬停在图标上会显示当前排除的程序、它是否在运行、输出设备是否正常。如果输出设备找不到，或被其他程序独占，会弹出通知、图标变成警告图标，并且每 2 秒自动重试，设备恢复后再弹出通知。
- **缓冲 / 延迟**：越小延迟越低，越大越不容易断音（电脑很忙时）。默认 20ms，详见下文“延迟”。旧版本的默认值是 12ms，已经保存在配置文件里的值不会自动改变，需要在菜单里手动选 20ms。
- **静音时输出微弱底噪**：打开后，没有声音时不再写入完全的数字零，而是写入约 -90dBFS 的 ±1 LSB 噪声（人耳听不到），有声音时也叠加同样的噪声。用途：有的接收端检测到一段连续的全零数据后会暂停编码，有声音时再重新开始，例如 RustDesk 约 8 秒全零后会停止编码；重新开始的那一下可能带来杂音。打开这个开关后接收端始终在编码。默认关，切换立即生效。
- **设置保存**在 `%APPDATA%\audio-exclude\config.json`（程序列表、当前选择、输出设备），下次启动时自动恢复并开始采集。配置文件损坏时会改名为 `config.json.bad`，然后用默认设置启动。
  设置环境变量 `AUDIO_EXCLUDE_CONFIG` 可以指定其他配置文件路径。
- 只能运行一个实例，否则两个实例会争抢同一个独占的输出设备。
- 目前没有开机自启动。需要的话，可以手动把 `tray.exe` 的快捷方式放进 `shell:startup` 文件夹。

## 命令行

```powershell
# 列出设备名
.\target\release\capture.exe --list-devices
# 排除 Discord，把其余声音写到虚拟声卡的播放端
.\target\release\capture.exe --exclude-name Discord.exe --output "Line 1 (Virtual Audio Cable)"
```

| 参数 | 含义 |
|---|---|
| `--exclude-name NAME.exe` | 按进程名排除。自动找到该名字的**根进程**（父进程不是同名进程的那个），排除整棵进程树，所以靠子进程出声的程序（Discord、浏览器）也能排除干净。每 250ms 检查一次，程序退出或重启后会自动重建采集；程序没在运行时转发全部声音。 |
| `--exclude-path PATH` | 按 exe 完整路径排除（规则与托盘程序相同）。 |
| `--buffer-ms N` | 抖动缓冲，默认 20，最小 11（见“延迟”）。 |
| `--silence-dither` | 静音时输出 ±1 LSB（约 -90dBFS）的底噪，而不是完全的数字零（同托盘菜单里的开关）。 |
| `--exclude-pid PID` | 按 PID 排除该进程树。 |
| `--output NAME` | 输出用的播放设备，默认 `Line 1 (Virtual Audio Cable)`。先按名字精确匹配，再找唯一的子串匹配。 |
| `--list-devices` | 列出播放设备和录音设备。 |

不带 `--exclude-*` 参数时转发全部系统声音。stdout 会输出状态行：`TARGET <pid>` / `TARGET none` / `READY`。
命令行版本出错时直接退出，不会重试。

### 配置 RustDesk

在被控端的 RustDesk 设置里，把 **音频输入（Audio input）** 设为虚拟声卡的**录音端**，
例如 `Line 1 (Virtual Audio Cable)` 或 `CABLE Output (VB-Audio Virtual Cable)`。
tray/capture 写虚拟声卡的播放端，虚拟声卡把声音送到对应的录音端，RustDesk 再从录音端读取。

## 测试

```powershell
cargo test -- --nocapture
```

测试在单机上用真实音频设备运行（不 mock），全部跑完约 30 秒，期间会从默认播放设备放出 -20dBFS 的测试音。
每个进程用不同频率的正弦波标记（被排除的 A 是 1000Hz，保留的 B 是 440Hz），用 Goertzel 算法测频点电平，
用 FFT 互相关测延迟。每次都同时录两路：虚拟声卡的录音端，以及测试音所在播放设备的 loopback（即本地实际听到的声音），后者作为参照。

| 用例 | 断言 |
|---|---|
| t1 按 PID 排除 | 440Hz 存在，1000Hz 比 440Hz 低 ≥40dB |
| t2 对照组 | 排除一个无关进程时，两个频率都到达虚拟声卡，电平与本地输出相差 <3dB |
| t3 无回环 | B 只播放 200ms；虚拟声卡里的声音不能比本地更响、更长，本地静音 80ms 后虚拟声卡也必须静音 |
| t4 进程重启 | 按名字排除，A 被杀掉后重新启动（PID 变化），仍然被排除 |
| t5 子进程出声 | A 本身不出声，由它启动的子进程出声；按名字排除根进程仍然有效 |
| t6 延迟 | 30ms 脉冲在本地输出与虚拟声卡之间做互相关（两路都按 QPC 时间戳对齐），断言 < 50ms |
| t7 按路径排除 | 两个**同名**程序放在不同文件夹，只排除指定路径的那个；它重启后仍然被排除 |
| t8 托盘程序 | 启动时恢复已保存的配置并排除；切换到“不排除”后再切回来，立即生效，并且配置文件已写回磁盘；构建并弹出右键菜单后程序不崩溃 |
| t9 输出出错重试 | 输出设备不存在、或被其他程序独占时报告错误，设备空出来后约 2 秒内自动恢复，声音照常 |
| t11 静音后出声 | capture 已经运行、5 秒什么都不播放之后，再开始播放正弦，从第一个采样起检查虚拟声卡里的波形有没有断点（模拟音量提示音） |
| t12 静音底噪开关 | 关：静音期间虚拟声卡里全是精确的零（行为不变）。开：没有一个采样是精确的零，电平 < -80dBFS；正弦照样无断点地通过 |
| t10 启动无杂音 | 一个连续的 1000Hz 正弦在播放时启动 capture，逐个采样检查虚拟声卡里的波形（纯正弦的二阶预测残差），启动后不允许出现断点、丢样或重复 |
| t13 快速连续点音量 | 连续的 1000Hz 正弦播放时，另一个流每 150ms 打开/关闭一次，共 20 次（模拟快速连点音量滑块）。Windows 每次都会丢一段音频，这找不回来；但虚拟声卡里不允许出现一个超过 t10/t11 阈值的硬台阶（丢失的两头必须是淡出/淡入） |

另有单元测试，覆盖路径规范化、根进程选择（包括 PID 被复用的情况）、配置文件的读写和修复。

托盘程序的这些部分**没有自动化测试**，需要手动验证：菜单的外观和点击、文件选择框、通知气泡、悬停提示，以及 Explorer 重启后图标能否恢复。
t8 通过发送与菜单项相同的命令 ID（`WM_COMMAND`）来驱动托盘程序；运行测试时不能有另一个 `tray.exe` 在运行。

参考实测值（Windows 10 19044 + VAC）：t1/t4/t5 的抑制量为 54–100dB，t6 的延迟约 37–42ms（缓冲 20ms）。

t10 会受到其他声音的干扰（被采集的是整个系统的声音），跑测试时请暂停其他音频。

| `AUDIO_EXCLUDE_MAX_LATENCY_MS` | 延迟阈值，默认 50 |

| `AUDIO_EXCLUDE_STATS=1` | capture/tray 每秒向 stderr 打印诊断：采集包、抖动缓冲水位、欠载、丢弃、漂移控制的速度；另外每次晚到/丢失的包、每次补静音、每次欠载都单独打印一行，带 QPC 时间 |
| `AUDIO_EXCLUDE_NO_TIMELINE=1` | capture/tray 关闭时间轴对齐（见下文），只用于新旧对比 |

| `AUDIO_EXCLUDE_T6_DELAY_MS` | t6 中脉冲在它的流打开之后多久播放，默认 500 |

## 延迟

端到端延迟（从本机实际播放到虚拟声卡录音端）由这几部分组成：

| 环节 | 约 | 说明 |
|---|---|---|
| Process Loopback 采集 | 10 ms | Windows 音频引擎每 10ms 交付一包，无法更小 |
| 抖动缓冲 | 约 15 ms（缓冲 20ms 时） | 比一包（10ms）多出的部分，用来吸收 Windows 丢失的音频（见下文） |
| 输出设备缓冲 | 约 6 ms | 维持在 5–7ms，另有 30ms 余量吸收线程调度延迟 |
| 虚拟声卡本身等 | 约 5 ms | 取决于虚拟声卡的设置 |

合计约 37–42ms（t6 实测，缓冲 20ms）。远控软件自身的编码、网络和播放缓冲通常比这大得多。

加入按时间戳补静音之后重测过更小的缓冲，各跑一次完整测试：12ms 时 t11、t12、t13 失败；15ms、17ms 时 t13（快速连续开关音频流，相当于连点音量条）分别有 4 处和 2 处断音；20ms 全部通过。延迟中位数分别为 31、32、39、41ms。所以默认值保持 20ms，15ms 适合只在乎延迟、能接受连点提示音时偶尔断音的场景。
（旧版本的 t6 读数是 34–38ms，但那是假象：t6 的脉冲在它自己的流打开 0.5 秒后播放，开流时丢掉的音频让旧版本的缓冲暂时变浅。把间隔改成 3 秒再测，新旧版本都是约 40ms。）

## 启动时 / 静音后出声时的杂音（已修复）

症状：远程那边听到的声音在刚开始的几秒有杂音，在一段静音之后突然出声（例如调音量时的提示音）最明显；本机播放是干净的。

早期版本把采集包直接写进一个轮询的独占缓冲，缓冲里只预留了很少的数据。启动后的头几秒，包的到达时间还不稳定，缓冲每秒会被播空好几次。
独占模式的缓冲被播空时，设备会**重放缓冲里的旧数据**，听起来就是杂音。实测第 1 秒 11 次欠载，之后 2、2、1、0 次。
在“静音 5 秒后出声”的场景（t11）中，旧版本在出声后的 0.3–1.8 秒内，虚拟声卡里出现了 6、5、1 处波形断点；新版本为 0、0、0。
现在的做法：
- 抖动缓冲攒够设定水位再开始播放，并且开头有 3ms 淡入。
- 输出线程每 1ms 补一次数据。
- 数据不够时只在设备快播空时才补**静音**，永远不会重放旧数据。

## 其他程序开始/停止播放时的断音（已修复）

症状同上：远程那边偶尔有“咔”的一声，在提示音这种“新开一个声音”的时候最容易出现。

原因：系统里**任何程序**打开或关闭一个音频流时，Windows 音频引擎会停顿一下，Process Loopback 因此**丢掉 4–15ms 的音频**（逐包记录：一个包晚到约 20–30ms，时间戳跳了同样多，数据却只有 10ms）。
丢掉的这段音频无论如何都找不回来，但旧版本的抖动缓冲还有一个问题：它没有办法把水位补回来。
每丢一次，余量就永久变少；默认 12ms 时余量只有约 2ms，几十毫秒后就会播空。播空时插入的静音和重新起播，就是听到的“咔”。

现在的做法：
- **漂移控制**：持续看抖动缓冲的平均水位。偏离目标时，用三次插值把播放速度放慢或加快一点，慢慢把水位拉回目标。偏差小时修正很轻（偏 2ms 只修正 0.1%），丢了一大段之后最多修正 0.5%（约 9 音分），10ms 的缺口大约 2–3 秒补回。回到目标附近后，恢复成逐个采样原样输出。
  这同时也解决了两个设备时钟的缓慢漂移。
- **默认缓冲改为 20ms**，留出约 10ms 余量，吸收一次丢失。

实测（整套测试，每档 6 轮）：旧版本缓冲 12ms 时 10 轮里有 7 轮在 t10/t11/t12 中查出断点；新版本缓冲 12ms 时 2/6，**20ms 时 0/6**，25ms 时 0/6。
（另外修了测试本身的一个 bug：每段录音里的**第一个**断点从来不会被统计，所以以前的测试漏报了单个断点。）

## 调音量提示音时的“滋啦”声（已修复）

症状：远程那边，用 RustDesk 的“System sound”完全没问题；用本工具时，点一下音量滑块就会有一点杂音，快速连点更明显。缓冲大小和静音底噪开关都没有影响。

原因：每个提示音都要打开、关闭一次音频流。每次打开或关闭，Windows 的 Process Loopback 都会丢一段音频：
- 下一个包的时间戳往前跳 0.4–12ms，**没有** `DATA_DISCONTINUITY` 标志。
- 如果这时有别的声音在播放，接下来还会有约 31ms 精确的数字零。

同样的情况下，设备 loopback（也就是 RustDesk 的“System sound”）一个样本都不丢。把采集缓冲加大到 5 秒（与 OBS 相同）也没有任何变化，所以这是 Windows 音频引擎本身的行为。
- 实测：另一个流每 150ms 开关一次，共 20 次。Process Loopback 有约 40 个时间戳空洞、80 处波形跳变；设备 loopback 是 0 和 0。
- 单个提示音：开流时（声音出现前约 25ms）丢一次，关流时（声音结束后约 120ms）再丢一次。

旧版本把包首尾相接，时间轴就短了一截，抖动缓冲的水位随之下降。漂移控制于是在接下来的 2–3 秒里重采样，恰好覆盖了整个提示音：一个静音之后的提示音，经过本工具后与原声的相关系数只有约 0.5–0.6。有别的声音在播放时，丢失的两头还是硬台阶。

现在的做法（`src/timeline.rs`，与 OBS 一样按时间戳放置音频）：
- **时间轴对齐**：从时间戳发现空洞（≥0.05ms），在缓冲里补上同样长的静音。水位不再因此下降，漂移控制只用来对付两个设备时钟的缓慢漂移。
- **软边**：如果丢失发生时有声音在播放，就把缓冲里还没播出的最后 3ms 淡出，声音回来时再用 3ms 淡入。时间戳没跳、但声音突然变成一串精确的零（至少 8 个样本）时，也按丢失处理。
- 抖动缓冲平时留着最后 3ms 不交出去，这样晚到的包报告丢失时，总还有可以淡出的数据。设备快播空时才交出这 3ms，并且同样淡出，所以真正的欠载也不再是硬切断。
- 输出设备的水位上调 1ms（5–7ms），抵消上面这 3ms 储备对设备缓冲余量的影响。
- **从不合成音频**：丢掉的部分就是静音，只是边缘是软的。
- 采集缓冲改为 5 秒（`LOOPBACK_BUFFER_MS`）。这只是容量上限，每次事件都会读空，不增加延迟。它没有消除空洞，但能防止系统卡顿时溢出，所以保留。

实测：
- 单个提示音（静音之后）：经过本工具后与设备 loopback 的相关系数 1.000，残差 -68dB，相当于原样通过（旧版本 0.48–0.67）。
- t13：硬台阶从 93–103 处降到 0（连续 6 轮）。

## 为什么输出必须用独占模式

Process Loopback 的 EXCLUDE 模式会采集**所有端点**上的共享模式流，其中也包括 capture 自己写进虚拟声卡的那一路。
如果用共享模式输出，声音会无限回环：t3 中 200ms 的脉冲会循环数秒，电平越叠越高。
独占模式流绕过 Windows 音频引擎的混音器，Process Loopback 看不到它，回环就不会出现。

## 已知限制

- tray/capture 运行期间**独占**虚拟声卡的播放端，其他程序不能同时往这条线播放。
- 只能排除**一棵**进程树（API 限制）。同名程序有多个独立的根进程时，只排除最早启动的那个。
- 采到的是端点音效（声卡的“增强”功能等）处理之后的声音。测试音使用 `AUDCLNT_STREAMOPTIONS_RAW` 播放，尽量绕开这些音效。
- 测试期间，系统里其他正在播放的声音会混进录音，可能影响 t1–t5 的结果，跑测试时请暂停其他音频。
- 有的安全软件（例如 ESET）在新程序第一次打开录音设备时会播放提示音，这个声音也会被采集进虚拟声卡，所以远程那边也可能听到。测试开始前会先等这类声音结束。
- Windows 的 Process Loopback 本身有一个现象：系统里**任何程序**开始或停止播放（哪怕是静音的流）时，它交付的数据里会有一个极小的台阶（约 -46dBFS）。这与本工具无关，用直接录原始 Process Loopback 的方式验证过。t10 用原始 Process Loopback 作参照，把这类台阶排除在外。
- 其他程序开流/关流时 Windows 丢掉的那一小段（有别的声音在播放时约 40ms）找不回来。本工具只能让它变成一个带软边的短暂静音，听起来是一次很短的音量下陷。
- 包晚到的时间超过余量（缓冲 20ms 时约 10ms）时，会有一次短暂的欠载（边缘同样是软的）。缓冲设得更大可以吸收更多，代价是延迟。
- 抖动缓冲比设定值多出 20ms 时，会丢弃最旧的数据，这时有一个极短的毛刺。有了漂移控制之后，这种情况基本不会发生。
- 漂移控制修正速度时，音高会有不超过 0.5% 的偏移，持续几秒。测试里的频点电平测量因此在 ±0.6% 的范围内取最大值。
- 进程名每 250ms 轮询一次，目标程序重启后最初约 0.25 秒的声音可能漏进虚拟声卡。
- 输出设备被拔掉或禁用时：托盘程序会提示并自动重试；命令行版本会报错退出。
